## 0. 为什么需要这份文档（Why）

v6.0 把 **Ontology 本体论** 定位为"统一抽象层"，但**只回答了"Ontology 是什么"，没回答"Ontology 怎么建模、按什么原理"**。当前出现 4 处形式化空洞：

| # | 空洞 | 后果 |
|---|---|---|
| 1 | PRD 写"12 Ontology Kernel"，SQL 建 3 张表，GraphQL 接口覆盖 2 类 | 命名分裂，团队无法对齐 |
| 2 | 顶层仅 4 元素（Entity / Relation / Action / Event），但与 12 Kernel 关系不明 | 不知道该往 ontology 里放什么 |
| 3 | JSONB schema 无类型系统、无约束推导 | 复杂业务（嵌套 / 引用 / derived）会撞墙 |
| 4 | 没说 Ontology First 怎么落地（强制 / 可选 / 谁审批 / 怎么 deprecate） | 19 应用迁移会各行其是 |

**目标**：把 Ontology 的形式化基础一次性钉死，让 PRD / SQL / GraphQL / PRD 改造有真值可循。

## 1. 核心 4 元组（Foundational Quadruple）

**主张**：v6.1 Ontology 由 4 个不可再分的**语义基元**组成。所有业务概念都必须落到这 4 个基元之一，不允许散落定义。

| 基元 | 语义 | 在 AgentOS 中的角色 | 例 |
|---|---|---|---|
| **Entity（实体）** | 可命名、可类型化、可独立标识的对象 | Agent / Skill / Tool / Workflow / Knowledge / User / Tenant / Asset | `customer:42`、`order:103` |
| **Relation（关系）** | 实体之间的依赖、组合、归属、调用 | Agent↔Skill、Skill↔Tool、Workflow↔Agent | `customer:42 -[has]-> order:103` |
| **Action（动作）** | 实体可执行的能力（可由系统或人触发）| `mp-ai` 模型推理 / `mp-ontology` 推理 / `mp-sandbox` 执行 | `customer.create`、`order.approve` |
| **Event（事件）** | 实体状态变化或外部信号的可观测记录 | `mp-monitoring` / `mp-audit` / `mp-frontend-obs` | `OrderApproved`、`LLMCallCompleted` |

> **重要**：这 4 个基元 ≠ 12 Kernel。4 元组是**语义层**，12 Kernel 是**类型层混淆**——详见 §3。

## 2. 类型系统基础（Type System）

### 2.1 三层模型

```
[ Type Layer ]   OntologyType    定义"是什么"     (schema/元数据)
      ↕  实例化（isa）
[ Instance Layer ]  Entity / Relation / Action / Event   业务数据
      ↕  归属（part-of）
[ Attribute Layer ] Attribute / State / Policy           实体的属性
```

- **Type**：可命名的 schema 定义，例如 `EntityType(customer)`、`RelationType(customer_has_order)`、`ActionType(customer.create)`
- **Instance**：类型的具体取值，例如 `Entity(id=42, type=customer, attributes={...})`
- **Attribute**：实例上的字段，**不是独立 Kernel**（详见 §3）

### 2.2 rid（Resource Identifier）等价性

- `rid` 是 Type 的**唯一标识符**，作用域 = `tenant_id`
- `rid` 一致 = 类型一致；`rid` 不一致 = 类型不同（即使 name 相同）
- **跨租户 rid 不相等**——A 租户的 `customer` 与 B 租户的 `customer` 是不同 Type
- 全局公共本体：`tenant_id IS NULL` 表示全局（仅平台预置 Customer/Order/Product/Contract 这 4 类）

### 2.3 继承（subTypeOf）

- Type 可以声明 `parent_type: text` 形成继承关系
- **协变规则**：子类型的 Attribute 集 ⊇ 父类型的 Attribute 集
- **逆变规则**：子类型 Action 的参数可**放宽**（optional 增多），不能收紧（required 减少）

### 2.4 实例标识

- **Entity**：`uuid`，业务上不可变
- **Relation**：`(from_id, to_id, relation_type)` 三元组唯一
- **Action**：`uuid`，并带 `triggered_by`（user/system/scheduled）+ `triggered_at`
- **Event**：`uuid`，并带 `source_entity_id` + `event_type` + `payload`（JSONB）

## 3. 12 vs 3 调整（修正 PRD 命名分裂）

### 3.1 主张：**4 Kernel，不接受 12**

PRD 现写 12 Ontology Kernel 是设计遗留错误——把"基元"和"派生概念"混为一谈。

| PRD 12 Kernel | 实际归属 | 是否独立建表 |
|---|---|---|
| **Entity** | 顶层基元（§1）| ✅ `ontology_object_types`（现有）|
| **Relation** | 顶层基元（§1）| ✅ `ontology_relation_types`（现有）|
| **Action** | 顶层基元（§1）| ✅ `ontology_action_types`（现有）|
| **Event** | 顶层基元（§1）| ❌ **缺表** — 需要新增 `ontology_event_types` |
| Attribute | **Entity 的字段**，不是 Kernel | ❌ 存于 `properties jsonb` 即可 |
| State | **Entity 的状态字段**，不是 Kernel | ❌ 存于 `properties jsonb.enum` |
| Role | **Relation 的子类型**（actor-of 关系）| ❌ 存于 `ontology_relation_types`（加 `role_kind` 字段）|
| Policy | **Action 的约束条件** | ❌ 存于 `ontology_action_types.policy jsonb` |
| Workflow | **Action 的编排**（Temporal workflow 名）| ❌ 存于 `ontology_action_types.workflow_name` |
| Document | **Entity 的描述** | ❌ 存于 `description text` + `mp-knowledge` |
| Tag | **Relation 的退化**（N:M 自关联）| ❌ 存于 `properties jsonb` |
| Comment | **Entity 的附注** | ❌ 存于 `description` 或独立 `audit_log` |

### 3.2 实际落地：4 Kernel

| Kernel | Type 表 | Instance 表（业务数据） |
|---|---|---|
| **EntityType** | `ontology_object_types` | `entities(id, tenant_id, type_name, attributes)` |
| **RelationType** | `ontology_relation_types` | `relations(id, tenant_id, from_id, to_id, relation_type)` |
| **ActionType** | `ontology_action_types` | `action_instances(id, tenant_id, type_rid, triggered_by, payload)` |
| **EventType** | `ontology_event_types`（**待新建**）| `events(id, tenant_id, type_rid, source_entity_id, payload)` |

> EntityType 的 `kernel_type` 字段将来要从 enum 12 值改为 enum 4 值。**v6.1 改造**：保留 12 值 enum 但加注释说明前 4 是真 Kernel、后 8 是历史遗留。

### 3.3 GraphQL 接口补齐

- 当前只覆盖 `Entity` + `Relation`，缺 `ActionInstance` + `Event` 的 Query/Mutation
- `KernelType` 枚举从 12 值改为 4 值 + `LEGACY_*` 前缀的 8 个历史值（向后兼容）

## 4. 约束体系（Constraints）

| 约束类型 | 表达位置 | 示例 | 违反时行为 |
|---|---|---|---|
| **基数约束**（cardinality）| `RelationType.cardinality` | `one_to_many` | 写入时 CHECK |
| **类型约束**（type match）| `RelationType.from_type / to_type` | `from=customer, to=order` | 写入时 CHECK |
| **属性类型** | `EntityType.properties.<field>.type` | `email: string` | Edge Function 校验 |
| **必填约束** | `EntityType.properties.<field>.required` | `email required` | Edge Function 校验 |
| **枚举约束** | `EntityType.properties.<field>.enum` | `status: [draft, active, archived]` | Edge Function 校验 |
| **函数依赖** | **v6.1 不实现** | `customer.email → customer.id` | v6.2+ |
| **业务规则** | `ActionType.policy jsonb`（DSL）| `if amount > 10000 → 需 owner 审批` | Temporal workflow 内 |

**实施分两阶段**：
- v6.1：基数 / 类型 / 属性类型 / 必填 / 枚举（5 类基础约束，DB 层 CHECK + Edge Function 校验）
- v6.2+：函数依赖、业务规则 DSL

## 5. Ontology vs Knowledge 边界（v0.2 重写）

> **重要更新**：v6.0 架构 spec §0 明确使用 **Microsoft GraphRAG**（KG + Leiden 社区 + 全局摘要），mp-knowledge PRD §2 写明 GraphRAG 负责"实体识别 + 关系抽取"。这意味着 Knowledge 层不是单纯的"向量检索 + BM25"，还有完整的 KG 子系统。

### 5.1 三层关系

```
┌─────────────────────────────────────────────────────────────┐
│  Ontology（mp-ontology）                                    │
│    ├─ 类型层：EntityType / RelationType / ActionType /      │
│    │          EventType（4 个真 Kernel，详见 §3）            │
│    └─ 实例层：entities / relations / action_instances /     │
│               events（被 GraphRAG 持续写入）                 │
└─────────────────────────────────────────────────────────────┘
                          ▲   ▲
                          │   │  类型校验 / OWL 公理校验
                          │   │
┌─────────────────────────────────────────────────────────────┐
│  Knowledge（mp-knowledge，GraphRAG + RAGFlow）              │
│    ├─ RAGFlow 子系统：文档解析 + BM25 + 向量                │
│    └─ GraphRAG 子系统：                                     │
│         ├─ LLM 实体抽取 ──┐                                 │
│         ├─ LLM 关系抽取 ──┤──→ 候选实例 ──→ OWL 校验 ──→   │
│         └─ Leiden 社区检测 │   写入 ontology 实例层         │
└─────────────────────────────────────────────────────────────┘
                          ▲
                          │
┌─────────────────────────────────────────────────────────────┐
│  RDF / OWL 形式层（v6.1 新增）                              │
│    ├─ TBox（Terminology Box）：ontology_*_types，OWL 公理   │
│    ├─ ABox（Assertion Box）：entities / relations，RDF 三元组│
│    └─ Reasoner（v6.1）：OWL2 RL 轻量推理                    │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 职责分工

| 层 | 职责 | v6.0 落地 | v6.1 补齐 |
|---|---|---|---|
| **Ontology 类型层** | schema / 约束 / 类型继承 / OWL 公理 | `ontology_*_types` 表 | OWL2 RL 公理声明 |
| **Ontology 实例层** | 业务数据 + GraphRAG 产出 + 手工数据 | **mp-knowledge 的 entities/relations 不重复建表**，直接写 ontology 实例层 | — |
| **Knowledge RAGFlow** | 文档切片 + 向量 + BM25 | `mp_knowledge.chunks` + pgvector | — |
| **Knowledge GraphRAG** | LLM 抽实体/关系 + Leiden 社区 + 全局摘要 | **不建独立 KG 表**，实体写入 ontology 实例层；社区与全局摘要写 `mp_knowledge.communities` | — |
| **RDF / OWL 形式层** | 三元组存储 + TBox/ABox + SPARQL-like 查询 | v6.0 不做 | v6.1 引入 |

### 5.3 关键设计：GraphRAG KG 与 Ontology 实例层合一

**问题**：mp-knowledge PRD §4 列了 `mp_knowledge.entities / relations / communities` 三张表，会与 mp-ontology 实例层（`entities / relations`）**命名分裂 + 数据冗余**。

**主张（v0.2）**：
- `mp_knowledge.entities` / `mp_knowledge.relations` **删除**——所有实体 / 关系只存于 ontology 实例层
- `mp_knowledge.communities` **保留**（Leiden 算法产出，不是 ontology 概念）
- mp-knowledge 在 ETL pipeline 里调 `mp-ontology.createEntity(type_rid, attributes)` 写入
- Ontology 实例层加 `source` 字段：`'manual' | 'graphrag_extract' | 'etl'`，溯源用

**好处**：
- 一处真值（ontology 实例层），GraphRAG 只是生产者之一
- 享受 RLS / 软删 / 审计 / OWL 约束，无重复 schema
- 19 应用迁移时，只读 ontology 就能拿到完整业务对象视图

## 6. 与形式化本体范式（OWL / RDF / DL）的关系（v0.2 重写）

> **重要更新**：v6.0 架构已用 GraphRAG，且业务需要语义级推理（如 subClassOf / equivalentClass / property domain-range）。PRD 写"不做 OWL/RDF"是错误决策。**本 spec 主张 v6.1 引入 OWL/RDF**。

### 6.1 三者定位

| 范式 | 在 v6.1 的角色 | 落地形态 |
|---|---|---|
| **OWL（Web Ontology Language）** | **类型层 schema 语言**——表达 `subClassOf` / `equivalentClass` / `ObjectProperty domain/range` / `cardinality restrictions` 等公理 | `ontology_*_types.owl_axioms jsonb`（JSON-LD / Manchester Syntax）|
| **RDF（Resource Description Framework）** | **实例层承载形式**——所有 entity / relation 都可表达为 `(s, p, o)` 三元组 | `rdf_triples` 表（PG 标准三元组表，详见 §6.3）|
| **Description Logic（DL）** | **推理形式化**——把 OWL 公理映射到 DL，做一致性 / 包含 / 分类推理 | v6.1 实现 **OWL2 RL** 子集推理（HermiT/Pellet 风格）|

### 6.2 与 GraphRAG 协同

GraphRAG 的 LLM 抽取产出是**候选实例**（可能违反 OWL 公理）。闭环流程：

```
[文档] → GraphRAG LLM 抽取
            ↓
        候选 entities / relations
            ↓
        OWL reasoner 校验
            ├── 通过 → 写入 ontology 实例层（rdf_triples）
            ├── 违反 → reject + 记录 conflict（mp-knowledge.communities.conflicts）
            └── 不确定 → 标记 pending + 入 HITL Hub（tool_dsh 类型）
```

### 6.3 RDF 三元组存储（v6.1 设计草案）

```sql
-- 单表三元组设计（PG 13+ 表分区可承接十亿级）
CREATE TABLE public.rdf_triples (
    id              uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
    tenant_id       uuid NOT NULL REFERENCES public.tenants(id) ON DELETE CASCADE,
    subject_id      uuid NOT NULL,                  -- entity.id
    predicate       text NOT NULL,                  -- OWL property name（如 'hasOrder'）
    object_id       uuid,                           -- entity.id（对象引用）
    object_literal  jsonb,                          -- 字面值（如 "active"）
    object_type     text NOT NULL DEFAULT 'iri'
                    CHECK (object_type IN ('iri', 'literal', 'datatype')),
    graph           text NOT NULL DEFAULT 'default', -- 命名图
    source          text NOT NULL DEFAULT 'manual'
                    CHECK (source IN ('manual', 'graphrag_extract', 'etl', 'import')),
    confidence      numeric(4,3),                   -- GraphRAG 抽取置信度 0.000~1.000
    created_at      timestamptz NOT NULL DEFAULT now(),
    -- 约束：object_id 与 object_literal 二选一
    CHECK ((object_type = 'iri' AND object_id IS NOT NULL)
        OR (object_type IN ('literal', 'datatype') AND object_literal IS NOT NULL))
);
CREATE INDEX rdf_triples_spo_idx ON public.rdf_triples (tenant_id, subject_id, predicate);
CREATE INDEX rdf_triples_pos_idx ON public.rdf_triples (tenant_id, predicate, object_id);
CREATE INDEX rdf_triples_osp_idx ON public.rdf_triples (tenant_id, object_id, predicate);

ALTER TABLE public.rdf_triples ENABLE ROW LEVEL SECURITY;
```

### 6.4 OWL 公理表达（`ontology_*_types.owl_axioms jsonb`）

```jsonc
// ontology_relation_types.properties 的 owl_axioms 字段示例
{
  "subPropertyOf": ["baseRelation"],
  "domain": ["customer"],       // OWL ObjectProperty domain
  "range":  ["order"],          // OWL ObjectProperty range
  "inverseOf": "orderBelongsTo",
  "characteristics": ["functional", "asymmetric"],  // OWL property characteristics
  "cardinality": "many_to_many"
}
```

```jsonc
// ontology_object_types.properties 的 owl_axioms 字段示例
{
  "subClassOf": ["entity", "auditableThing"],
  "equivalentClass": "any customer with email set",
  "disjointWith": ["order", "product"],
  "hasKey": ["email"],
  "propertyAssertions": [
    {"property": "email",    "cardinality": "exactly 1", "range": "xsd:string"},
    {"property": "hasOrder", "cardinality": "min 0",     "range": "order"}
  ]
}
```

### 6.5 OWL2 RL 推理范围（不实现 OWL2 DL 全集）

| OWL2 RL 子集能力 | v6.1 是否实现 |
|---|---|
| `subClassOf` 分类（hierarchical classification）| ✅ 实现 |
| `subPropertyOf` 继承 | ✅ 实现 |
| `equivalentClass` 等价类展开 | ✅ 实现 |
| `ObjectProperty domain/range` 校验 | ✅ 实现 |
| `property characteristics`（functional/transitive/symmetric）| ✅ 实现 |
| `cardinality restrictions` | ⚠️ 仅 0/1 边界，复杂 cardinality v6.2 |
| `disjointWith` | ✅ 实现 |
| `inverseOf` | ✅ 实现 |
| OWL2 DL 全集（SROIQ）| ❌ v6.2+ |

**Reasoner 形态**：**不引入外部 reasoner**（避免部署依赖），实现一个**轻量规则引擎**（约 50 条 RBox/TBox 规则），基于现有 RDF 三元组 + OWL 公理跑前向推理。

### 6.6 与 GraphQL / SPARQL 接口分层

| 接口 | 服务 | 角色 |
|---|---|---|
| **GraphQL** | mp-ontology（主）/ PostgREST（次）| 业务 CRUD / 关系查询 / 投影 RDF 子集 |
| **SPARQL-like** | Edge Function 封装 | v6.1 引入，支持跨类型三元组查询（受限于 PG 索引）|
| **OWL 公理编辑** | mp-ontology GraphQL + 审批 | 注册 / 修改 OWL 公理走 `pending_object_changes` 流程 |

**原则**：业务应用走 GraphQL；知识图谱深度分析（GraphRAG / Leiden 内部）走 SPARQL-like；OWL 公理编辑走审批流。

## 7. Ontology First 落地规则

### 7.1 强制建模 vs 可选建模

| 场景 | 是否必须先建模 |
|---|---|
| mp-runtime / mp-platform 的核心业务对象（订单/合同/审批…）| **必须** |
| mp-ai / mp-workflow / mp-knowledge 内部用对象 | 可选 |
| mp-monitoring / mp-audit 的可观测对象 | 可选 |
| 临时 ETL 落地表 | 不需要 |

### 7.2 命名规范

- Type `rid` 全小写、下划线分隔（`customer_has_order`）
- Action `rid` 用点分（`customer.create`、`order.approve`）
- `name` 字段用业务中文名（`客户`、`订单`）
- 全局公共 rid 必须经 `ontology-gen` 流程审批（见 ADR-0056）

### 7.3 版本化与 deprecate

- 任何 schema 变更必须升级 `version` 字段（`v1` → `v2`）
- `status='deprecated'` 标记后，旧版本实例仍可读但禁写
- 跨版本兼容由 Edge Function 校验
